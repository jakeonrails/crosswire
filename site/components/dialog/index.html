cw.dialog

CSS over the shipped native <dialog> widget — ::backdrop, @starting-style enter/exit transitions, :modal sizing, and internal scroll containment. The modal-composition showcase: no new markup, no new presenter, styles cw.dialog as-is.

site/examples/dialog/composed-with-card.html.erb

<%# The modal-composition showcase (ui-tier-spec.md §5 item 8): cw.dialog_for
    (compose-yourself) driving a real cw.button trigger and a cw.card body — three
    styled-tier components stacked on one dialog, still fully wired by
    Crosswire::Presenters::Dialog underneath. No new API: `d.trigger_attrs` and
    `d.close_attrs` are the SAME hashes `_dialog.html.erb` itself merges onto plain
    <button> elements; here they merge onto cw.button instead. %>
<%= cw.dialog_for id: "gallery-dialog-composed", labelled_by: "gallery-dialog-composed-title" do |d| %>
  <div <%= cw_attrs(d.root_attrs) %>>
    <%= cw.button "Delete project…", variant: :danger, **d.trigger_attrs %>

    <dialog <%= cw_attrs(d.panel_attrs, class: "cw-dialog__panel") %>>
      <button <%= cw_attrs(d.close_attrs, class: "cw-dialog__close") %>>&times;</button>
      <%= cw.card variant: :outlined do |c| %>
        <% c.header { tag.h2 "Delete this project?", id: "gallery-dialog-composed-title" } %>
        <% c.body { "This removes it for every collaborator. There is no undo." } %>
        <% c.footer { cw.button "Cancel", variant: :ghost, data: { action: "click->cw--dialog#close" } } %>
      <% end %>
    </dialog>
  </div>
<% end %>

Props

No declared variants — CSS-only styling of the existing primitive; see its own keyword arguments.

Morph contract

Morph: Server-owned
  DOM-only state: the `<dialog>` element's OWN modal state — its `open`
    attribute vs. whether `showModal()`/`close()` has actually been called on it.
    `open:` is rendered server-side (R4), and the controller's `#render` calls
    `showModal()`/`close()` from that value on connect — the two are meant to
    agree, but per the HTML spec they CAN diverge: removing the `open` attribute
    does NOT call `close()`.
  On morph: this is exactly the divergence a background morph can cause. Turbo
    8's Idiomorph gives `open` no special handling, so a morph that strips it
    from a currently-open `<dialog>` would leave the document `inert` (from the
    earlier `showModal()`) with no visible, reachable modal and `close()` reduced
    to a silent no-op — the page goes dead. The controller does not rely on a
    `usePreserve` guard for this: it cancels `turbo:before-morph-element` on the
    panel outright while open (so Idiomorph never touches it mid-modal at all)
    and closes the dialog itself on `turbo:before-cache`, so a page snapshot
    never depicts a live modal as dead markup. A second, narrower guard
    (`turbo:before-morph-attribute`, the seanpdoyle turbo#1239 fix) cancels only
    the `open` attribute's own removal as defence-in-depth. Proven against real
    `@hotwired/turbo`, not merely asserted, in `test/js/dialog_controller.browser.test.js`.
  The app must: always render the CURRENTLY correct `open:` server-side on every
    response that could be followed by a morph — the controller's own defence
    stops a BACKGROUND morph from killing an already-open dialog, but a page-level
    navigation/redirect still trusts whatever `open:` the next response sends.

CSS

/* crosswire/ui/dialog.css — CSS over the shipped `_dialog.html.erb` widget
   (Crosswire::Presenters::Dialog): the modal-composition showcase (ui-tier-spec.md §5
   item 8). NO markup, NO presenter, NO helper change — every class below already
   exists on the shipped partial (cw-dialog / cw-dialog__trigger / cw-dialog__panel /
   cw-dialog__title / cw-dialog__close / cw-dialog__body), and this file only paints
   them. Every color/length below is either a global token or one of THIS component's
   own `--cw-dialog-*` knobs, always consumed through `var(...)` — see tokens.css's own
   header for the override ladder.

   `.cw-dialog__panel` IS the native `<dialog>` element (see the partial) — every rule
   below that targets it is therefore also styling `::backdrop`, `:modal` and
   `@starting-style`, none of which exist on any other kind of element. */

@layer crosswire.components {
  .cw-dialog__trigger {
    /* Deliberately no chrome of its own — compose `cw.button` for a styled trigger
       (see site/examples/dialog/composed-with-card.html.erb); this knob exists so a
       host CAN restyle the bare default without ejecting. */
    --cw-dialog-trigger-font: inherit;

    font: var(--cw-dialog-trigger-font);
  }

  .cw-dialog__panel {
    --cw-dialog-bg: var(--cw-color-surface-raised);
    --cw-dialog-fg: var(--cw-color-fg);
    --cw-dialog-border: var(--cw-color-border);
    --cw-dialog-radius: var(--cw-radius-lg);
    --cw-dialog-padding: var(--cw-space-5);
    --cw-dialog-gap: var(--cw-space-4);
    --cw-dialog-width: min(32rem, calc(100vw - var(--cw-space-6)));
    --cw-dialog-max-height: min(85vh, 40rem);
    --cw-dialog-enter-scale: 0.96;
    --cw-dialog-enter-offset: 1rem;
    --cw-dialog-backdrop: var(--cw-color-overlay);

    /* The panel is its own flex column so the title/close row can stay put while
       .cw-dialog__body (below) is the ONE thing that scrolls internally — "internal
       scroll containment" per the showcase brief, rather than letting a tall body
       grow the panel past the viewport. `position: relative` makes it an explicit
       positioning root for .cw-dialog__close below, rather than depending on
       whatever `position` the UA stylesheet happens to give a top-layer <dialog>. */
    position: relative;
    display: flex;
    flex-direction: column;
    gap: var(--cw-dialog-gap);
    margin: auto;
    border: var(--cw-border-width) solid var(--cw-dialog-border);
    border-radius: var(--cw-dialog-radius);
    padding: var(--cw-dialog-padding);
    background: var(--cw-dialog-bg);
    color: var(--cw-dialog-fg);
    font-family: var(--cw-font-sans);
    font-size: var(--cw-text-sm);
    line-height: var(--cw-leading-normal);
    box-shadow: var(--cw-shadow-3);
    max-height: var(--cw-dialog-max-height);

    /* `transition-behavior: allow-discrete` keeps the panel PAINTED (rather than
       vanishing the instant `open` is removed) for the duration of the opacity/
       transform transition below — the modern CSS-only dialog open/close recipe.
       `@starting-style` supplies the FROM state for the enter transition (fires on
       "newly rendered from display:none/closed", regardless of whether the dialog
       was opened by a trigger click or a controller call); the EXIT transition is
       simply this same rule running backwards as `[open]` is removed. */
    transition: opacity var(--cw-duration-base) var(--cw-ease),
                transform var(--cw-duration-base) var(--cw-ease),
                overlay var(--cw-duration-base) var(--cw-ease) allow-discrete,
                display var(--cw-duration-base) var(--cw-ease) allow-discrete;
  }

  /* :modal — only a dialog opened via showModal() (the presenter's `modal: true`
     default) gets this pseudo-class; a non-modal panel (`modal: false`, opened via
     show()) keeps the browser's normal static-flow box instead of being centered
     and width-capped like this. */
  .cw-dialog__panel:modal {
    inset: 0;
    width: var(--cw-dialog-width);
  }

  .cw-dialog__panel:not([open]) {
    opacity: 0;
    transform: scale(var(--cw-dialog-enter-scale)) translateY(var(--cw-dialog-enter-offset));
  }

  @starting-style {
    .cw-dialog__panel:modal {
      opacity: 0;
      transform: scale(var(--cw-dialog-enter-scale)) translateY(var(--cw-dialog-enter-offset));
    }
  }

  /* ::backdrop only exists for a MODAL dialog (showModal()'s top layer) — a
     non-modal panel (show()) never gets one, so nothing here needs to guard for
     `modal: false`. Same allow-discrete/@starting-style shape as the panel itself,
     so the dim-in and the panel's own enter transition read as one motion. */
  .cw-dialog__panel::backdrop {
    background: var(--cw-dialog-backdrop);
    transition: opacity var(--cw-duration-base) var(--cw-ease),
                display var(--cw-duration-base) var(--cw-ease) allow-discrete,
                overlay var(--cw-duration-base) var(--cw-ease) allow-discrete;
  }

  .cw-dialog__panel:not([open])::backdrop {
    opacity: 0;
  }

  @starting-style {
    .cw-dialog__panel[open]::backdrop {
      opacity: 0;
    }
  }

  .cw-dialog__title {
    margin: 0;
    padding-inline-end: var(--cw-space-6);
    font-size: var(--cw-text-lg);
    font-weight: var(--cw-weight-semibold);
    line-height: var(--cw-leading-tight);
  }

  .cw-dialog__close {
    --cw-dialog-close-size: var(--cw-text-lg);

    position: absolute;
    top: var(--cw-space-3);
    right: var(--cw-space-3);
    display: inline-flex;
    align-items: center;
    justify-content: center;
    appearance: none;
    border: 0;
    padding: var(--cw-space-1);
    background: transparent;
    color: var(--cw-color-fg-muted);
    cursor: pointer;
    font-size: var(--cw-dialog-close-size);
    line-height: var(--cw-leading-tight);
    border-radius: var(--cw-radius-sm);
  }

  .cw-dialog__close:hover {
    color: var(--cw-color-fg);
    background: var(--cw-color-surface-sunk);
  }

  /* The one thing that scrolls — see the panel's own flex-column comment above.
     `scrollbar-gutter: stable` (the same property `cw--dialog`'s own scroll-lock
     reaches for on the page behind the modal) reserves the scrollbar's track up
     front, so content does not visually reflow the instant a tall body actually
     needs to scroll. */
  .cw-dialog__body {
    overflow-y: auto;
    scrollbar-gutter: stable;
  }

  @media (prefers-reduced-motion: reduce) {
    .cw-dialog__panel,
    .cw-dialog__panel::backdrop {
      transition: none;
    }
  }
}
